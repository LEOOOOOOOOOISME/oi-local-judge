## 0. 一句话目标

让一个**不熟悉命令行的老师**，在只准备 **题面/限制 + std + generator** 的情况下，能在系统内完成：

> 编译检查 → 数据计划 → 生成 `.in` → 跑 std 出 `.out` → 校验 → 预览 → 发布题包

并且出题人随时能在页面内看到“下一步做什么、为什么失败、怎么修”。

## 3. 出题体验（本轮最高优先级）

### 3.1 设计原则

1. **最小输入原则**：出题人只需要题面、限制、std、generator；其余由系统推导或给默认值。
2. **每一步可解释**：失败必须指出“哪个测试点、哪条约束、怎么修”，不能只给一个 SE。
3. **默认安全**：自动推导的时限/内存只能比出题人设定更宽松或相等，不能更紧；不能静默改配置。
4. **可回退**：每次生成产生版本快照；重新生成只覆盖选中测试点，不误删已确认数据。
5. **离线优先**：AI 提示词只做复制粘贴，不默认联网；帮助中心完全离线。
6. **AI 不自动发布**：AI 生成代码必须出题人编译、试跑、审核后才能进入正式数据。

### 3.2 端到端向导

```text
新建题目
  → 填题面/限制/题型
  → 上传 std.cpp + generator.cpp
  → 系统编译并做契约检查
  → 选择数据计划模板（或自动生成）
  → 一键生成并校验
  → 预览测试点/子任务/统计
  → 修复失败点（可只重跑失败点）
  → 发布题目/加入比赛
```

#### 步骤 1：新建题目

必需：

- 标题、题型（传统/文件 IO；交互/SPJ/客观题走各自流程）
- 题面（Markdown + LaTeX）
- 时间限制、内存限制、输出限制
- 子任务/分值（可先用自动模板，后改）

可选：

- validator、checker、brute、std 的额外编译参数
- 样例（可从题面代码块提取）
- 标签、难度、来源

#### 步骤 2：上传 std + generator

系统立即做：

- 扩展名/大小/语言检查
- g++ 编译（`-O2 -std=c++17`；C 用 `gcc`）
- 静态检查：是否读写文件、是否联网、是否使用 `rand()`/`random_device`/时间、是否有 `system()`/`popen`
- generator 契约检查：是否有 `registerGen`、是否接受 seed 参数
- 给出“通过/警告/阻断”三态

#### 步骤 3：数据计划

系统提供模板：

- **10/30/60**：10% 样例/边界，30% 小数据，60% 大数据
- **Subtask 阶梯**：每个子任务一组，逐级扩大范围
- **最大/最小/随机/构造**：边界、极限、随机、特殊构造
- **自定义**：JSON 或可视化表单

默认自动分配：

- 测试点数量：10~30（按题目类型和限制）
- 分值：子任务均分或按模板，总和 100
- seed：连续整数；每组独立
- 参数：从题面约束提取 min/max；提取不到则要求出题人填

#### 步骤 4：生成并校验

后台任务（不占正式评测位），逐点执行：

```text
generator --seed S --group G --index I > case.in
std < case.in > case.out
validator < case.in
check std exit code / time / memory / output size
hash case.in, detect duplicates
```

进度展示：当前组、当前点、已用时间、失败原因、日志。

#### 步骤 5：预览

每个测试点展示：

- 输入/输出前 100 行（可展开）
- 文件大小、行数、hash
- std 运行时间/内存
- 所属子任务、分值、依赖
- 重复/空文件/超限警告

子任务汇总：

- 测试点数、总分、覆盖的约束
- std 最大用时/内存
- 与时限/内存的余量

#### 步骤 6：修复与重跑

- “只重跑失败点”
- “只重跑某个子任务”
- “改 generator 参数后重跑整组”
- 保留上一次成功数据，直到新数据通过校验
- 每次生成写版本快照（1.2 完整版本历史；1.1 至少保留最近 3 次）

#### 步骤 7：发布

发布前必须过质量门禁（见 3.5）。发布后：

- 题面/数据/配置写入题包
- 记录生成参数、seed、std/generator hash
- 可导出 OiJudge/Lemon/Cena 题包

### 3.3 Data Plan 模型

最小 JSON（高级模式）：

```json
{
  "schema": "oijudge.data-plan/1",
  "limits": { "timeMs": 1000, "memoryMb": 256, "outputMb": 64 },
  "groups": [
    {
      "id": "sub1",
      "name": "基础",
      "points": 30,
      "count": 5,
      "seedStart": 1,
      "args": ["--n=10", "--m=10"],
      "dependsOn": []
    },
    {
      "id": "sub2",
      "name": "大规模",
      "points": 70,
      "count": 10,
      "seedStart": 1001,
      "args": ["--n=100000", "--m=200000"],
      "dependsOn": ["sub1"]
    }
  ],
  "pointsMode": "group",
  "naming": "{group}-{index}"
}
```

约束：

- `points` 总和必须等于题目满分（默认 100）
- `dependsOn` 必须无环
- `count` 总和受磁盘/时间预算限制
- `seedStart + count` 不得溢出
- `args` 必须是字符串数组，禁止 shell 拼接；服务端按 argv 传递

### 3.4 std / generator 契约

完整模板与检查清单见 [std-generator-contract.md](../../help/authoring/std-generator-contract.md)。

#### std 契约

- C++17（C 用 C11），标准输入/输出
- 不读写文件、不联网、不调用系统命令
- 不使用随机数、时间、未定义行为
- 使用 `long long`/`__int128` 防溢出
- 复杂度满足题面约束；递归深度可控
- 必须通过样例和所有生成数据
- 运行时间/内存必须留有余量（建议 ≤ 限制的 50%）

#### generator 契约

- C++17 + `testlib.h`
- `registerGen(argc, argv, 1)`
- 必须支持：
  - `--seed=<int>`
  - `--group=<string>`
  - `--index=<int>`
- 只使用 `rnd`，禁止 `rand()`/`random_device`/时间
- 只写 stdout，不写文件
- 输出必须在题目限制内
- 同一 seed 必须产生完全相同的输出
- 生成时间必须可预算（默认单点 ≤ 2s，可配）

如果出题人的 generator 不接受这些参数，系统提供两种适配：

1. 包装脚本（推荐）：把 `--seed/--group/--index` 转成旧参数
2. 环境变量：`OIJ_SEED`、`OIJ_GROUP`、`OIJ_INDEX`（兼容旧工具）

但“无法注入 seed”的 generator 不能用于正式比赛数据，只能做一次性导入。

### 3.5 质量门禁

发布前必须全部通过：

| 门禁 | 规则 | 失败处理 |
|---|---|---|
| 编译 | std/generator/validator/checker 全部编译成功 | 阻断，展示编译错误 |
| 确定性 | 同一 seed 生成两次，sha256 相同 | 阻断，提示去掉随机源 |
| 非空/可读 | 输入非空、UTF-8、行尾规范 | 阻断 |
| 大小 | 单文件/单题不超限 | 阻断 |
| validator | 有 validator 时全部通过 | 阻断 |
| std | 所有测试点 AC，exit 0 | 阻断 |
| 时限余量 | std 最大用时 ≤ 时限 × 0.5 | 警告；> 0.8 阻断 |
| 内存余量 | std 峰值 ≤ 内存 × 0.5 | 警告；> 0.8 阻断 |
| 重复 | 输入 hash 不重复 | 警告；重复率 > 10% 阻断 |
| 子任务 | 覆盖率、分值、依赖合法 | 阻断 |
| 样例 | 样例输入/输出与题面一致 | 阻断 |
| 总预算 | 生成总时长/磁盘在预算内 | 阻断 |

没有 validator 时：

- 系统执行“格式/边界检查”（行数、整数范围、文件大小、空行）
- 显示黄色警告：“未提供 validator，无法保证语义约束”
- **CF-like 赛制或接受 Hack 的题目**：发布/开赛前必须补 validator，否则阻断
- 其他比赛/练习题：允许发布，但记录风险标记
- 组卷人/比赛管理员可在比赛题目配置中追加/覆盖 validator，不改原题；Hack 判定优先使用该覆盖，缺失则用题目 validator

### 3.6 限制配置与余量警告

- **时限/内存/输出限制由出题人手动填写**；系统不自动改写。
- 系统实测 std 后展示：最大用时、峰值内存、最大输出、与限制的余量。
- 余量 < 50%：绿色；50%~80%：黄色警告；> 80%：红色并阻断发布。
- 测试点数量：默认给 10/30/60 或子任务阶梯模板，出题人可改。
- 分值：默认按子任务均分；可改为逐点。
- 系统可以提供“参考值”文本，但不自动填入；所有最终值由出题人确认。

> 选择“手动填 + 警告”而不是“自动建议 + 确认”，是为了避免系统把 std 的实现缺陷误当成题目限制。

### 3.7 AI 提示词系统

目标：出题人把题面/约束粘进提示词，得到**可编译、可验证**的 std/generator/validator/brute/checker 草稿。

产品形态（1.1）：

- 出题页每个资产旁有“AI 提示词”按钮
- 抽屉展示：模板选择、输入变量、完整提示词、复制按钮
- 只做复制，不默认调用任何外部 API
- 复制后可粘贴到任意 AI；生成代码再粘回资产编辑器
- 粘贴后自动编译/试跑；失败可复制“修复提示词”

提示词模板必须包含：

- 角色、题目信息、输入/输出格式、数据范围、子任务、样例
- 编译器/标准/时限/内存
- 输出格式约束（只输出一个代码块）
- 禁止项（文件 IO、联网、随机、未定义行为）
- 自检清单

完整模板见 [ai-prompts.md](../../help/authoring/ai-prompts.md)。

AI 代码的边界：

- 不自动发布
- 不自动加入正式数据
- 必须通过编译、样例、生成数据、validator、人工审核
- 不把学生代码/个人信息发给外部 AI
- 如果未来接入外部 API，必须默认关闭、管理员配置、审计

### 3.8 出题体验验收

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AUT-EXP-01 | 新老师只给 std + generator | 30 分钟内生成 3 子任务、20 测试点并发布 |
| AUT-EXP-02 | generator 编译失败 | 1 分钟内看到具体错误和修复建议 |
| AUT-EXP-03 | std 在某点 TLE | 定位到具体测试点、用时、限制，可只重跑该点 |
| AUT-EXP-04 | 输入重复 | 重复 hash 列表、重复率、可删除/重生成 |
| AUT-EXP-05 | 未提供 validator | 普通题警告；CF-like/Hack 题阻断；组卷人可补 validator |
| AUT-EXP-06 | AI 生成 std | 复制提示词→粘贴→编译→样例通过；不自动发布 |
| AUT-EXP-07 | 重新生成 | 只覆盖选中测试点，其他不变 |
| AUT-EXP-08 | 题包导出 | 生成的测试点、子任务、分值、依赖完整保留 |

- `HelpTip`：字段旁的 `?`，悬浮/点击显示 2~5 行 + “阅读全文”
- `HelpDrawer`：右侧抽屉，展示完整文章，不离开当前页面
- `HelpLink`：错误提示/空状态里的“怎么修”
- `HelpChecklist`：开赛前/出题前的可勾选清单

### 4.6 引导式教程

- 首次进入管理端：3 步 checklist（建题 → 生成数据 → 建赛）
- 首次出题：高亮“上传 std/generator → 数据计划 → 生成”
- 首次开赛：高亮“名单 → 开始 → 封榜 → 结束”
- 可跳过、可重看、不阻塞操作
- 1.1 先做 checklist + HelpTip；完整 tour 可 1.2

### 4.7 技术方案（建议）

- 文档源：`docs/help/**/*.md`，随仓库版本管理
- 构建：Vite 构建时生成 `help-index.json`（标题/锚点/纯文本/标签/角色/路由）
- 渲染：复用 `markdown-it` + `markdown-it-texmath` + `katex` + `sanitize-html`
- 搜索：`minisearch`（MIT），中文 bigram 自定义 tokenizer
- 代码高亮：文档代码块懒加载 `shiki`（MIT）或复用 `highlight.js`；不阻塞首屏
- Tour：`react-joyride`（MIT）优先；若包体敏感改用 `driver.js`（MIT）
- 不引入 Docusaurus/VitePress/Nextra 作为应用内文档站：它们是独立站点，和 Electron 离线/单页应用不匹配；可作为未来公开文档站

## 8. 已确认与仍需拍板

### 8.1 已确认（2026-11-02）

| 问题 | 结论 |
|---|---|
| 1.1 范围 | **并行加人**，出题体验/帮助中心与 P0 并行推进，不延期 |
| validator | **CF-like 或接受 Hack 的题目必须有 validator**；其他比赛可选；组卷人可补充/覆盖，不改原题 |
| generator 契约 | **强制 testlib + `--seed/--group/--index`**；旧工具用环境变量/包装层适配 |
| AI 形态 | **只提供可复制提示词，完全离线**；不默认调用外部 API |
| AI 发布边界 | **人工审核 + 编译 + 试跑后才能发布**；AI 代码不自动发布 |
| 帮助中心内容源 | **仓库 Markdown + 构建期索引**；1.1 不做 CMS/独立文档站 |
| 数据生成任务 | **独立后台任务**，可取消/重跑，不占正式评测位 |
| “std+generator”范围 | **只覆盖传统/文件 IO**；交互/SPJ/客观题走各自流程 |
| GitHub 复用 | **只复用 MIT/BSD/Apache 并保留声明**；GPL/AGPL 只参考 |
| 时限/内存 | **出题人手动填写 + 余量警告**；系统不自动改写 |
| 测试点数量/分值 | **10/30/60 或子任务模板 + 可编辑** |
| 帮助中心角色 | **全角色 + 角色过滤** |
| validator 覆盖权限 | **组卷人/比赛管理员**可追加/覆盖；setter 不直接改比赛配置 |
| Hack validator | **比赛覆盖 > 题目 validator**；没有覆盖则用题目 validator |

## 9. 风险

1. **“只给 std+generator”是营销口号，不是充分条件**：题面、限制、子任务仍不可或缺；CF-like/Hack 题还必须有 validator。文档必须诚实。
2. **数据生成可能很慢**：30 个点 × 2s std + generator，4C/8G 上可能几分钟；必须后台、可取消、有预算。
3. **AI 生成代码不可信**：必须人工审核 + 编译 + 试跑；不能自动发布。
4. **帮助中心容易腐烂**：文档必须跟版本、跟截图、跟错误码；否则比没有更糟。
5. **GitHub 复用有许可证风险**：AGPL/GPL 项目只能参考；必须记录第三方声明。
6. **1.1 范围仍大**：出题体验 + 帮助中心 + P0 修复 + 4C/8G + 安装包；如果性能验收不过，先冻结功能。
7. **并行加人有协调成本**：出题/帮助中心与 P0 共享同一数据模型和权限边界，必须锁定接口后再并行，否则会互相返工。
